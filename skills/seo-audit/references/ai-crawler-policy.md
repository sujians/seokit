## Verification steps

1. **Confirm goals.** Identify public product, category, application, and capability pages intended for search discovery and AI retrieval. Evaluate training permission, automated search, and user-triggered access independently. Record restrictions in relation to the owner’s goals and mark unknown intent for confirmation.
2. **Check origin and path.** Record the scheme, host, port, and tested path with query, and the `/robots.txt` status, final URL, and truncation. Check product paths and language subdomains separately. Consider soft 404s and access challenges when the file request returns 200 HTML. A reported 404 or 410 means no rules file was found on this check. Evaluate 403, 429, 5xx, network errors, and truncation against platform policies and available evidence. [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html) · [Google robots.txt handling](https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt)
3. **Record effective rules.** Use `robots.bots` for access outcome, dedicated or wildcard group, and matching rule. For Googlebot, check `robots.groups`, merging same-name dedicated groups if present and using the wildcard group otherwise. Use the most specific path match and prefer `Allow` at equal specificity. Check encoding, wildcards, and the end anchor. Flag incomplete rules and ambiguous cases for retest. [Google matching and precedence](https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt#order-of-precedence-for-rules)
4. **Locate conflicts.** Propose scoped changes for affected crawlers and public paths only when the effective automatic search rule conflicts with a confirmed goal. Verify actual platform access through site logs, official verification methods, or public crawler IP data. Protect restricted prices, drawings, tests, and customer records with authentication or permissions. [Google crawler verification](https://developers.google.com/crawling/docs/crawlers-fetchers/verify-google-requests)
5. **Check llms.txt.** Record `llms.status`, `llms.url`, `llms.exists`, and truncation. The tool probes presence using HTTP status and response format. Read the file explicitly to evaluate content, structure, and links. The optional proposal can point to stable, public catalogs, specifications, applications, and qualifications. Google Search AI features use existing Search technical requirements. [llms.txt proposal](https://llmstxt.org/) · [Google Search AI features](https://developers.google.com/search/docs/appearance/ai-features)
