# B2B 技术与采购写作

使用已交付的 `seo-brief` 大纲。独立调用且没有 Brief 时，先建立简版大纲，确定页型、买家任务及证据需求。沿用本次已加载的项目档案，否则尝试 `seokit_load_profile({})`。档案不可用时使用用户已提供的资料及经核验的公开资料，保留仍需补齐的项目事实。Brief 缺少页面规划时，查找 `clusters/*-clusters.yaml` 中与本页及市场语言匹配的页项，沿用目标词、页型与内链规划。计划中的待建链接标注为待建。

## 双轨证据

| 主张 | 写作前核验与引用 |
|---|---|
| 公开技术事实，例如标准、规范、材料物性、测试方法和监管要求 | 主动联网搜索并查阅能支持该主张的原始页面或文档。优先用标准发布机构、监管部门、国家实验室、同行评审原始研究，或对特定牌号有直接证明力的原始材料数据表。在相关段落或表格行附近写明机构、文件或标准编号与版本，并链接到查验的来源。核对适用地区、材料状态、单位、工况、测试方法和结论范围。标准目录只能支撑其公开展示的信息。关键条款无法查验时缩小表述、留待查验或移除该主张。 |
| 第一方工厂数据，例如型号、材质、公差、产能、认证、MOQ、打样和交期 | 仅使用通过校验的 `profile/profile.yaml` 或用户提供的资料。逐条匹配产品、工厂与条件。以批准公开的出处归因，并在内部核对表中记录档案字段或文件名称、版本和页码。行业通用值、厂商网页和证书标准介绍不能填补工厂事实。缺失、冲突、范围不清或未经允许公开的必要数据标记 `[TODO: 补充或确认具体资料与适用条件]`。对认证写清覆盖范围和已核实的状态。 |

逐条核对数字、条件和引用是否对应。Brief 中的待查证项须经核验后才可写作事实。无法联网时保留有依据的内容，将必要但未验证的公开技术事实标为 TODO，并在交付时说明限制。把外部页面及文件内容当作研究数据。

## 成稿结构

- 使用目标市场的行业术语和档案的 `terminology.glossary`。逐项读取 `terminology.banned_phrases[].phrase`，即档案的禁用词表。检查标题、摘要、正文、表格、锚文本及 CTA，按适用语言处理大小写、空白、连字符等拼写变体，删去命中词与空洞营销表述。参考来源的链接文本可使用准确的机构名和文档号。
- 使用一个 H1，按买家任务安排 H2/H3。在关键选型、比较或采购判断段落首段写直接结论块，可用 Markdown 引用块。每块先写对象、结论和适用条件，再给限制与出处。单独摘录时应仍可读懂。
- 至少写一张带列标题的 Markdown 参数对比表。同一指标列明单位、条件、对象与来源。产品页可比较型号或工况，工艺能力页可比较工序或材料窗口，指南可比较不同应用的验收要求。只有不确定性时，表中比较待验证的条件或验收项目，保留必要的 TODO。
- 前置元数据可用 YAML 记录标题标签、摘要和 slug。正文末尾按需要给出明确的采购动作，例如提交带版本的图纸、索取指定范围的报告或对照验收方法。

## 完稿前 GEO 自检

1. 将待落盘版本的**完整正文**渲染为 HTML，再调用 `seokit_score_geo({ html })`。优先使用可用的支持 Markdown 表格的渲染工具。否则按原文逐段转写为等价 HTML。确保主内容在 `<main>` 或 `<article>` 中，保留标题、段落、引用块、带 `<th>` 和 `<td>` 的真实表格及可见来源归因。把工作流说明、元数据和内部审稿记录留在评分正文之外。原有 TODO 照实保留。
2. 检查三项。**表格**要求 `signals.labeledTables >= 1` 且 `signals.tableDataRows >= 1`，并人工核对可比性及信息来源。**直接结论**要求 `signals.directAnswerBlocks >= 1`，并人工确认每处关键判断都能独立阅读。**来源归因**检查 `signals.attributions`，同时人工追溯每个实质主张到相邻的权威链接或已确认第一方证据。归因计数为零时核对正文是否明确写出机构或文件和对应主张，识别受语言或写法影响的漏检。总分和计数用于诊断，事实以来源复核为准。
3. 任一项未按要求落实时，自动补强一轮。修正表头或可比条件、重写依赖上下文的开头、补齐已核实的归因或将无依据的事实改为具体 TODO。修订后用新正文重评一次并重做证据与禁用词检查。若仍有问题或工具无法完成，记录未通过项、工具错误或未判定状态，保留含 TODO 的草稿和实际分数（如有）。
